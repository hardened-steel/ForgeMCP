Потоки работы

Каждое действие проходит предсказуемый путь

Пользователь видит инструмент. Внутри ForgeMCP проверяет запрос, применяет предметные правила, а затем — при необходимости — запускает только утверждённую программу. Ниже показаны главные жизненные циклы.

Запись: только через Workspace + CASЗапуск: только через ProcessRuntimeДлительная работа: progress — наблюдение, не управление

Чтение и изменение файла

SHA-256 здесь играет роль «версии содержимого»: команда меняет ровно тот файл, который до этого видела. Это защищает от тихой перезаписи чужой параллельной правки. Патч может создать отсутствующий файл только при явном null-ожидании; удаление и переименование отсутствуют в публичном API.

После изменения: согласованность CMake и clangd

1. Workspace публикует факт

Событие содержит относительный путь, тип изменения, метаданные снимка и номер поколения — но никогда содержимое файла.

2. CMake оценивает актуальность

Изменение CMakeLists.txt, .cmake, preset или рабочего toolchain-файла делает профиль stale. Автоматический configure не запускается.

3. clangd синхронизируется

Для отслеживаемого документа отправляется один полный didChange; диагностические данные и временные handles устаревают. Новая база компиляции может вызвать контролируемый restart.

Важная тонкость: успешный configure, закончившийся после нового изменения входного файла, тоже помечается устаревшим. Это консервативно: ForgeMCP предпочитает сказать «нужна проверка», а не выдать сомнительно свежий результат.

Observer распознаёт только строгие форматы Ninja и CTest или периодические heartbeat-сообщения. Сырые строки компилятора не становятся MCP-ответом или сообщением прогресса. Если клиент медленный или отключился, прогресс выключается лишь для данного запроса; сама сборка и результат сохраняют прежние правила.
