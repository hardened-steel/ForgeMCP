# ForgeMCP 0.3.0

This release adds a local browser administration panel for multiple independent
ForgeMCP server sessions, with invocation history, existing MCP App widgets, and
service monitors.

## Changes

- Normal CLI launches automatically join one admin Hub for the current OS user.
  Each server keeps its own workspace, environment, toolsets, managed processes,
  CMake state, and clangd sessions. The panel gives each instance a separate tab.
- Invocation history records calls from both the original MCP client and the
  browser, including arguments, results, progress, timestamps, status, and errors.
  Select a call to inspect its original widget, readable text, or complete JSON.
- The panel displays startup settings, process summaries, discovered toolsets,
  CMake configurations, and retained clangd sessions. Its catalog exposes existing
  tool schemas, resources, resource templates, and resource reading.
- Command controls are initially disabled. Enable them to call an existing tool
  with literal JSON arguments or cancel a running command initiated by the panel.
  SDK elicitation requests from browser operations can be answered in the panel;
  requests from an original MCP client remain owned by that client.
- Browser operations use a persistent in-process SDK client connected to the same
  registered MCP server. They retain existing handler validation, request context,
  and feature concurrency rules. Services initialize and close once per runtime.
- Added `local_ipc`, which hides Windows named pipes and Unix sockets behind a
  duplex byte-frame interface. Windows pipes use explicit current-user permissions
  and reject remote clients; Unix sockets use a private user directory and peer
  identity checks.
- The Hub starts automatically, reconnects surviving instances after connection
  loss, and exits shortly after the final server session ends. Open browser tabs
  do not keep it alive. PID and process birth-time checks distinguish a temporary
  disconnect from a completed session. Lost commands are never replayed
  automatically.
- Widgets run through an isolated Apps host on a separate loopback origin. Each
  widget can read only immutable resources linked by its selected invocation and
  cannot execute tools or browse arbitrary resources.
- Fixed the widget connection failure displaying “Unable to connect to the host.”
  IPC serialization now omits absent optional MCP fields while preserving explicit
  JSON null values in arguments, schemas, and structured results. Default history
  IDs, timestamps, and progress arrays are retained.
- Added focused regression tests for local IPC, SDK wire serialization, and the
  Apps initialization handshake, result delivery, linked-resource access, and
  cancellation of a pending connection.

Open the panel while at least one server is running:

```powershell
forgemcp --open-admin
```

The command discovers the private browser URL through local IPC and opens the
system browser. Authentication tokens remain in memory and are not printed or
stored in a token file. HTTP listens on `127.0.0.1`, with browser session, origin,
and CSRF checks. Port 8765 is preferred; an available port is chosen if needed.

Additional operator options are:

```powershell
forgemcp --no-admin
forgemcp --admin-port 9000
forgemcp --admin-ipc forgemcp-other
forgemcp --open-admin --admin-ipc forgemcp-other
```

History and linked result resources remain in each instance's memory and disappear
when it stops. There is no database or history archive. Settings are read-only.
Shared source/build directory coordination between independent instances remains
outside this release's scope.

## Installation

Requires Python 3.13 or newer:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install forge-cpp-mcp==0.3.0
.\.venv\Scripts\forgemcp.exe --workspace C:\Projects\Example
```

The attached wheel can also be installed directly:

```powershell
.\.venv\Scripts\python.exe -m pip install .\forge_cpp_mcp-0.3.0-py3-none-any.whl
```

On macOS/Linux, use `.venv/bin/python` and `.venv/bin/forgemcp`.
The wheel includes the admin panel, isolated Apps host, compiled widgets, and
icons. Node.js is required only for source builds. New runtime dependencies for
the HTTP host and process identity checks are installed with the package; pywin32
is installed on Windows. Install CMake, compilers, Ninja, and clangd separately as
needed.
The attached source distribution includes frontend sources and the npm lockfile;
`SHA256SUMS` covers both packages. Early-development limitations from 0.2.0 remain.
